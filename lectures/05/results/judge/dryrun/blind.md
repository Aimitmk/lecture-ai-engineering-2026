## D001（context_saving）

質問：第3回で紹介された、エージェントのコンテキストを節約したり、あふれないようにしたりする工夫をすべて挙げてください

要点：p1=サブエージェント：調べものを別のエージェントのコンテキストで行い、親には要約した報告だけを入れる / p2=ツール検索：ツールの定義を最初から全部入れず、必要なものだけ読み込む / p3=コンパクション：古い履歴を要約に置き換える / p4=Skill：コンテキストには名前と説明だけを入れ、手順の本文は使うときに読み込む

```text
第3回で紹介された、エージェントのコンテキストを節約したり、あふれないようにしたりする工夫として、以下のものが挙げられます。

1. **サブエージェントの活用**
   - 調べものなどの細かい作業を別のエージェント（サブエージェント）に切り分けて任せることで、親エージェントのコンテキストに大量の検索結果やファイルの中身がたまらないように節約する（第3回・PDF p.31）。
2. **ツール検索（Tool search）の利用**
   - 多数のツール定義を最初からすべてコンテキストに入れるのではなく、常に入れておく「ツールを探すツール（`tool_search`）」を使い、必要なときに見つかった定義だけをコンテキストに読み込ませる（第3回・PDF p.32）。
3. **メモリ（外部の保存先）の利用**
   - 有限であるコンテキストから、過去の重要なやり取りや決定事項（テストの実行方法やコーディング規約など）を外の保存先（ファイルやデータベースなど）に書き出し、必要なときに新しいコンテキストへ戻して参照する（第3回・PDF p.13, 38-39）。
4. **コンパクション（履歴の要約）の利用**
   - コンテキスト（ループの中の履歴）があふれないよう、古い履歴を要約してコンパクトに詰め替える（第3回・PDF p.39, 65）。
```

## D002（forget_long）

質問：会話や作業が長くなると、モデルが途中の情報や前の指示を見落とすのはなぜですか。講義ではどんな対策を紹介していますか

要点：p1=長い文脈を均等には使えず、途中（真ん中）の情報ほど使われにくい（Lost in the Middle、U 字型） / p2=第2回の対策：資料を全部渡さず、関係する部分だけを検索して渡す（RAG）／要約や作業メモで情報を整理する／入力の長さを変えて正答率が落ちないか測る / p3=第3回：エージェントでは、作業が長くなると前の指示や経緯を見落とす。Part 6 メモリで扱う

```text
会話や作業が長くなるとモデルが途中の情報や前の指示を見落とすのは、**「長い文脈を、均等には使えない（真ん中にある情報ほど使われにくく、正答率がU字型に下がる）」**という基盤モデルの仕組み上の限界があるためです（第2回・PDF p.3, p.15）。また、チャットにおいて会話が続いて見えるのは、毎回これまでのやり取りの全文（コンテキスト）をすべて送り直しているという背景もあります（第3回・PDF p.8）。

講義では、こうした長い文脈における見落としや限界に対する対策として、以下のような方法が紹介されています（第2回・PDF p.15）。

* **関係する部分だけを渡す（RAG）：** 講義資料などを全部まとめて渡すのではなく、質問に関係する部分だけを検索して渡す。
* **要約や作業メモで情報を整理する：** 長い会話や資料では、要約や作業メモを活用して情報を整理する。
* **入力の長さを変えて評価する：** 入力の長さを変えて、正答率が落ちないかを測る。
```

## D003（publish_ok）

質問：開発者が自分で100問ほど試して95問が正しそうだったら、そのチャットボットを公開してよいですか

要点：p1=それだけでは評価として十分ではない（そのまま公開してよいとは言えない） / p2=理由1：平均だけでは分からない。本番のデータは開発時と変わる（質問の種類で正答率が違う、開発者は典型的なユーザーではない、想定外が起こる、モデルは劣化する） / p3=理由2：速度やコストなど、機能以外の要件（非機能要件）がある / p4=理由3：本当に減らしたいのは講師の負担。正答率などの技術の指標だけでなく、価値の指標で測る

```text
講義資料によると、LLMは確率で次の言葉を選ぶ仕組みであるため、答えが揺れたり、知らないことももっとらしく答えてしまったりすることがあります（第2回・PDF p.16〜17）。そのため、1回のテストで正解だったとしても、それはたまたまかもしれません（第2回・PDF p.17）。

開発者が100問ほど試して95問が正しそうだったという状況について、講義資料では以下のような点が指摘されています。

* **確率的な揺れへの注意**: 答えは確率で揺れるため、同じ質問を何回か聞き直したり、答えられない質問も含めたりして複数回測る必要があります（第2回・PDF p.16〜17）。
* **自分の評価セットの重要性**: 公開ベンチマークや一般的な成績ではなく、自身の用途に合わせた「自分の評価セット」を用いて、実際の質問への正答率や、分からない質問に「分かりません」と言えるかを確認することが大切です（第2回・PDF p.39）。

公開してよいかを判断するにあたっては、「95問正解した」という1回限りの結果だけで判断するのではなく、以下のような点を確認してみましょう。

* 同じ質問を何度か繰り返したときも安定して正解するか？
* モデルが知らない質問や答えられない質問が混ざったとき、知ったかぶりをせずに「分かりません」と適切に答えられるか？
```

## D004（rag_or_ft）

質問：講義資料に答えるチャットボットを作るとき、RAGとファインチューニングはどう使い分ければよいですか

要点：p1=知識（新しい事実・資料にしかない事実）は、検索して渡す（RAG）。FT で知識を覚えさせるのは非効率で、誤りが増える報告もある / p2=振る舞い（出力形式・口調・手順）は、プロンプトで直らなければ FT を検討する / p3=判断の順番：評価セットで測る → 知識か振る舞いかを分ける → プロンプトで直るか試す → それでも直らない振る舞いに FT

```text
講義資料によると、RAGとファインチューニング（FT）の使い分けの基本線は**「知識」か「振る舞い（答え方）」か**という基準で考えます（第2回・PDF p.46）。

* **知識の追加（新しい事実や資料など）**
  * **RAGが向いています。**
  * 新しい知識や変化する情報（今日の講義内容や毎年の課題の締切など）をモデルに覚えさせるのは、FTでは非効率であり、ハルシネーション（誤り）が増える傾向があるため、まず資料を検索して渡すRAGが効果的とされています（第2回・PDF p.46, p.47, p.57）。
* **振る舞いの修正（出力形式、口調、手順の守り方など）**
  * **ファインチューニング（FT）が向いています。**
  * 「必ず決まったJSON形式で返す」「特定の口調や手順を守らせる」といった答え方のルールは、まずプロンプトで指示し、それでも直らない場合に手本を与えてFTを行います（第2回・PDF p.46, p.57）。
```

## D005（forget_long）

質問：会話や作業が長くなると、モデルが途中の情報や前の指示を見落とすのはなぜですか。講義ではどんな対策を紹介していますか

要点：p1=長い文脈を均等には使えず、途中（真ん中）の情報ほど使われにくい（Lost in the Middle、U 字型） / p2=第2回の対策：資料を全部渡さず、関係する部分だけを検索して渡す（RAG）／要約や作業メモで情報を整理する／入力の長さを変えて正答率が落ちないか測る / p3=第3回：エージェントでは、作業が長くなると前の指示や経緯を見落とす。Part 6 メモリで扱う

```text
会話や作業が長くなるとモデルが途中の情報や前の指示を見落としてしまう理由と、講義で紹介されている対策は以下のとおりです。

### なぜ見落としてしまうのか
* **長い文脈を均等には使えない性質**
  * LLMは一度に読める入力の長さが伸びていても、文脈の真ん中あたりにある情報ほど使われにくいという傾向（U字型になりやすい特徴）があります。そのため、資料や会話の途中に重要な情報や指示があっても、見落とされやすくなります（第2回・PDF p.15）。

### 講義で紹介されている対策
チャットボットや長い会話・資料における対策として、以下の方法が挙げられています（第2回・PDF p.15）。

* **関係する部分だけを渡す（RAG）**
  * 講義資料などをすべてまとめて一度に渡すのではなく、質問に関係する部分だけを検索してモデルに渡す手法です。
* **要約や作業メモで情報を整理する**
  * 長い会話や資料のなかで、要約や作業メモを活用して情報を整理・維持します。
* **入力の長さを変えて正答率を測る**
  * 実際に自分の用途やデータの長さにおいて、正答率が落ちていないかを測定・評価します。
```
