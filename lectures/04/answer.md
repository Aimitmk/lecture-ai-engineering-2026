  - 上位のモデルは thinking を使う（1 件あたり平均 568 トークン）。出力の前に内部で考えるなら、「理由を先に書かせる」の効き目は、もともと小さいかもしれない。
- 上位のモデルは、2・3 回目で #05 根拠を unsure にした。
  - 2 回目の理由は「参照の期待するふるまいにて一般論を説明するかどうかは「まだ決めていない」とされている」で、参照を挙げている。
  - 3 回目は参照の名前を出さず、「採点基準でまだ決まっていません」とした。参照の「採点の基準ではまだ決めていない」と同じ言い方だが、rubric.md にはもう方針がある。
  - #05 の参照（`data/eval/lec04_cases.jsonl`）には、今も「一般的な説明をするかどうかは、採点の基準ではまだ決めていない」とある。演習の STEP 3 で、rubric.md には方針を書き足したが、参照の文は変えていなかった。
  - 採点者には rubric.md と参照の両方が渡る。2 つが食い違っていると、判定が揺れうる（1 回目は「基準に適合」として pass、2・3 回目は unsure）。
  - ただし、pass と unsure の分かれ目は、13:43 の 1 回目と 20:30 からの 2・3 回目の分かれ目と、ちょうど重なる。時間帯の違いによる揺れとは区別できない。
  - それでも、方針を決めたら、rubric.md だけでなく参照の「期待するふるまい」も合わせて直すべきだった。
  - flash-lite は 12 回とも pass だった。ただ、STEP 3 の前（方針が無いとき）も pass だったので、方針に従った結果かどうかは分からない。
- 指定したモデル名（gemini-3.5-flash）と、応答したモデル（gemini-3.6-flash）が違った。
  - 名前が同じでも、中身のモデルが変わることがある。
  - 採点の結果には、応答に記録されたモデル名を残しておく必要がある（今回は `.raw.jsonl` に残した）。
- LLM のずれは、ほとんどが過検出（厳しすぎる側）で、見逃しは 1 回だけだった。この評価セットでは、採点器は甘いより厳しい。
  - ただし、ラベルが fail の項目は基準ごとに 1 件しかないので、見逃しにくいのかどうかは、この件数では言えない。
- 疑問：判定の順序の効き目を確かめるには、キーの順を保つ出力で同じことをする必要がありそう。
  - たとえば、tool 出力ではなく Gemini の JSON 出力モード（pydantic-ai の `NativeOutput`）を使う。
  - あるいは、thinking を使わないモデルにそろえる。

- 回答の様子（第3回のエージェント）：

  - #07 は、「第5回の要点はまだ用意されていない」と答え、内容は推測しなかった。

**コードで判定した方がよい基準と、LLM に任せる基準の使い分け**

| 基準 | 判定 | 理由 |
|---|---|---|
| 回の表示（末尾に第N回） | コード | 文字列で決まる。ただ、「なし」「対象外」を合格にするかのような意図は、規則に書かないと決まらない |
| 期待したツールを呼んだか（道筋） | コード | 最終回答の文には残らない。LLM の採点者に渡るのは質問・回答・参照だけなので、LLM には判定できない（#09） |
| 保存の前に承認を求めたか | コード | 取り消しにくい操作の安全の基準。承認待ち（`DeferredToolRequests`）が出たかで決まる。回答の言い方（「承認が必要ですが」）に頼るべきでない |
| 根拠（参照と矛盾しない・断定しない） | LLM | 言い換えや要約が正しいかは、文字列の照合では決まらない。ただ、参照に無い情報（回の要点データ）は LLM も照らせないので、参照に入れる必要がある |
| 範囲・ヒント | LLM | 断り方や、どこまで書けばヒントかは、文脈で決まる |
| 分かりやすさ | LLM（参考） | 主観的。rubric.md の具体例が、言葉の手がかりとして効きすぎる（#02）。総合に入れないのは妥当 |

- 考え方：答えが 1 つに決まるもの（形式・道筋・承認）はコードで、読んで意味を判断するものは LLM で判定する。
- コードの判定は、何度流しても同じになる。LLM は、実装の 10 件では 3 回同じだったが、演習の 10 件では揺れた（基礎）。

**気づき・疑問**

- 自分のエージェントの回答には、LLM で判定する 4 基準の不合格が、1 件も無かった（Claude のラベル）。
  - そのため、採点器が不合格を見逃すかどうかは、この 10 件では測れない。
  - 講師の評価セットのように、わざと失敗した回答を混ぜる必要がある（回答を手で壊す、指示を弱めたエージェントで作る、など）。
- 採点のモデルと、回答を作ったモデルが同じ（gemini-3.5-flash-lite）。自分の出力を甘く見る偏りがあるとしても、不合格が無い 10 件では確かめられない。
- 評価のハーネスには、人の確認を挟むエージェントの扱いを決めておく必要がある。
  - `generate_answers` は、承認が要るツールのあるエージェントを想定していなかった。
  - 扱い方は、断る・承認する・止まったことを記録する、などがある。今回は断って、承認を求めたことを記録した。
- 疑問：#09 のように「答えは正しいが、決められた手順（用語集の確認）を踏んでいない」回答は、合格にしてよいか。
  - 最終回答だけを見る評価では合格、道筋も見る評価では不合格になる。
  - どちらを合格の条件にするかは、評価を設計する側が決めることだと思う。

- LLM が解くとしたら何が難しいか（Claude の見立て。実行して確かめてはいない）：
  - 症状が出る所と、直す所が離れている。直す行は少なくても、探す範囲が広い。
    - matplotlib：長い `hist()` の中で、引数の辞書が上書きされている所を直す。
    - django：ORM が集約をサブクエリにする条件を直す。
    - pytest：症状は xdist で出るが、直すのは pytest 本体のシリアライズ。
  - 既存の機能を壊してはいけない。PASS_TO_PASS（直す前も後も通るべきテスト）が 19〜411 件あり、1 つでも落ちると不正解になる。
  - テストはエージェントに見せない。issue の文だけから、テストが期待する形（関数名や戻り値）に合わせる必要がある。

    - FAIL_TO_PASS は `test_arcsin` の 1 件だけ。
    - test_patch には他の分布のテスト（新しく足された `test_long_precomputed_cdf` など）も入っているが、FAIL_TO_PASS にも PASS_TO_PASS にも入っていない。
    - そのため、採点を通っても issue が全部直ったとは限らない可能性がある（理由は確かめていない）。

**作成と検証の人数・手順**

- 元の SWE-bench（2023、論文の 3 段階の手順）
  - 12 の人気 Python リポジトリから、PR を約 9 万件集めた。
  - その中から、issue を解決していて、テストのファイルも変えている、マージ済みの PR を選んだ。
  - 最後に実際に実行して、「直す前に落ち、直した後に通るテスト（FAIL_TO_PASS）」が 1 つ以上あるものだけを残した（2,294 件）。
  - 問題文と正解（パッチとテスト）を書いたのは、各リポジトリの利用者と開発者。ベンチマークの作者は、集めて機械的に選んだ。
- SWE-bench Verified（2024、OpenAI と SWE-bench の作者）
  - 注釈したのは、Python の経験がある**プロのソフトウェア開発者 93 人**。
    - OpenAI のエンジニアが確信を持ってラベルを付けた 50 件で試験を作り、合格した人だけが参加した。
    - どこから集めた人かは、記事にも手順書にも書かれていなかった。
  - 元のテストセットからランダムに選んだ **1,699 件**に、**1 件 3 人**で注釈した。公開 CSV では、注釈が 5,097 件、注釈した人が 93 人。
  - 見たことは 2 つ（どちらも 0〜3 の 4 段階）。
    - issue の説明が足りているか
    - FAIL_TO_PASS のテストが、正しい解答まで落とさないか
    - ほかに大きな問題があれば書き、難易度（直すのにかかる時間）も見積もった。
  - 落とし方：
    - 3 人のうち**いちばん重いラベル**を採った。どちらかが 2 以上か、大きな問題の指摘があれば落とした。
    - その結果、**68.3% が落ちた**（説明不足が 38.3%、テストが不公平が 61.1%）。CSV で数えると、1,699 件中 1,160 件が落ち、539 件が残った。
  - 500 件の選び方：残りから、1 時間以上かかる 45 件を全部入れ、あとはランダムに選んだ。
    - 500 件の内訳は、<15 min 194・15 min〜1 hour 261・1〜4 hours 42・>4 hours 3（データから数えた）。
    - OpenAI の記事の今の版は「<15 分が 196 件」と書いているが、データでは 194 件。食い違いの理由は分からなかった。
- 採点の方法：**テストの実行**。
  - エージェントのパッチを当て、FAIL_TO_PASS と PASS_TO_PASS の両方が通れば「解決」とする（Docker の環境で実行）。
  - テストはエージェントに見せない。LLM 採点は使わない。
- その後：OpenAI は 2026-02-23 に、SWE-bench Verified の数字を報告するのをやめた、と書いた。理由は 2 つ。
  - 汚染：試したフロンティアモデルは、一部の問題で正解のパッチや問題文をそのまま再現できた。公開の GitHub から作ったデータなので、事前学習に入っている。
  - 欠陥：o3 が 64 回の試行で安定して解けなかった 138 問を調べると、59.4% で、テストか問題文に重大な問題があった（テストが狭すぎる・広すぎる、など）。

**今日の評価セットとの違い**

| | 今日の評価セット（演習） | SWE-bench Verified |
|---|---|---|
| 規模 | 10 件 | 500 件（注釈は 1,699 件） |
| 作り手 | 講師 1 人。質問も、回答（失敗を仕込んだもの）も講師が用意 | 実際の GitHub の issue と PR。問題文・正解のパッチ・テストは、各リポジトリの利用者と開発者が書いた |
| 検証の人数 | 講師 1 人のラベル（参考）と、受講生 1 人のラベル（今回は Claude） | 93 人。1 件 3 人で、いちばん重い判定を採用 |
| 落とした件数 | 落としていない（失敗の例を意図して入れている） | 1,699 件中 68.3% |
| 採点の方法 | 人のラベルと LLM の採点（根拠・範囲・ヒント・分かりやすさ）、コード（回の表示） | テストの実行だけ（コード） |
| 測っているもの | エージェントが指示どおりにふるまうか。採点器を信じてよいか | issue を直せるか |

- 似ているところ：
  - どちらも、基準を文章で書いた手順書で人がラベルを付け、決めにくいものは落とすか人に回している。
  - Verified の 0〜3 の基準と「いちばん重い判定を採る」は、今日の unsure を自動判定から外すのと同じく、迷ったら厳しい側に倒す作り。
- 違うところ：
  - Verified では、採点はテストで決まり、LLM も人も採点しない。
  - ただ、テストが狭すぎれば正しい解答を落とし、広すぎれば誤った解答を通す。
  - これは今日の「回の表示」（コード）と同じで、コードの判定は決定的だが、測りたいこととずれることがある（演習 #07 の「なし」を不合格にする）。

**気づき・疑問**

- 何千件ものデータでも、検証の中心は「人が基準に照らして読む」ことだった。
  - 人を増やし（93 人）、1 件を複数の人で見て（3 人）、試験で人の判定をそろえて（50 件）、ラベルのぶれを抑えている。
  - 今日のように 1 人で付けたラベルでは、人同士でどれだけ割れるかを測れない。
- 1 件 3 人で見ても、2026 年の再調査では、難しい問題の多くに欠陥が見つかった。
  - 評価セットは、一度検証したら終わりではない。
  - モデルが強くなって解けない問題が目立つようになると、そこから欠陥が見えてくる。
- 公開したデータは、公開したこと自体で汚染されうる。今日の 10 件も公開の repo にあるので、後のモデルの学習に入れば、同じ問題で測っても意味が変わる。
- 疑問：sympy の例のように、FAIL_TO_PASS が要求の一部しか確かめていない問題がある。
  - Verified の注釈が見たのは「テストが正しい解答を落とすか」で、こうした問題は見つけにくい。
  - 「誤った解答や不完全な解答を通してしまうか」は、誰がどう確かめているのか。
  - UTBoost（arXiv 2506.09289）などの研究は、テストが足りないために誤ったパッチが通っている例を報告している。
